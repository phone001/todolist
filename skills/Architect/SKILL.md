# 기술 설계 (Architect)

## 목적

확정된 기획 및 요구사항을 기술적으로 분석하여 개발자가 구현에 사용할 수 있는 설계 문서를 작성한다.

이 Skill의 결과는 실제 구현물이 아니라 **설계 문서**다.
실제 소스코드, 데이터베이스, API, 화면, 설정 등을 변경하지 않는다.

---

# 기본 원칙

- 설계 전에 기획 산출물(`document/planner/plan.md`)이 설계 가능한 수준으로 올바르게
  기획되었는지 먼저 검증한다. 누락·모호·충돌이 있으면 미결정 사항으로 Orchestrator에 반환한다.
- 기존 시스템과 관련 코드를 먼저 조사하고, 기존 구조와 컨벤션을 최대한 활용한다.
- 요구사항에 필요한 설계 영역만 작성한다.
- 서비스 정책이나 요구사항을 임의로 결정하지 않는다. 기술적 결정에는 가능한 한 근거를 기록한다.
- 기술 스택(언어/런타임, 프레임워크, 주요 라이브러리, DB 엔진, 캐시/검색/메시징 등 인프라성 컴포넌트)은
  "가정"으로 남기지 않고 명시적으로 선정하며 근거와 검토한 대안을 기록한다.
  기존 코드베이스가 있으면 그 스택을 따른다. 런타임과 주요 라이브러리는 major 버전을 고정한다.
- 설계 산출물은 **overview / logic / database / nfr 4종으로 한정**한다.
  별도의 api / frontend / integration / infrastructure 문서를 만들지 않는다.
- API 설계는 `logic.md`의 「API 설계」 섹션에 작성하며, API 사용이 필요 없으면 작성하지 않는다.
- 보안 설계는 `logic.md`의 「보안 설계」 섹션에 반드시 포함한다.
- 각 문서 간 내용이 서로 모순되지 않도록 검증한다.

금지 사항은 문서 하단 「금지 사항」에 정리한다.

# 작업 절차

## 1. 기획 산출물 검증 및 요구사항 분석

`document/planner/plan.md`를 읽고, 요구사항이 올바르게 기획되었는지 그리고
설계 가능한 수준인지 확인한다.

- 원본 사용자 요청 / 상위 요구사항이 기획서에 빠짐없이 반영되었는가
- 기능 목적 / 기능 범위 / 사용자 흐름 / 서비스 정책이 명확한가
- 입력 및 출력 / 상태 변화 / 예외 조건 / 기존 기능과의 관계가 정의되어 있는가
- 비기능 요구사항(성능, 가용성, 확장성, 관측성, 보안/개인정보)이 기술되어 있는가
- 요구사항 간 충돌·모순이 없는가
- 가정과 확정 사항이 구분되어 있는가
- Acceptance Criteria가 검증 가능한 형태인가

설계에 필요한 기획 또는 정책이 누락·모호·충돌한 경우 임의로 결정하지 않고
미결정 사항(반려 사유)으로 기록하여 Orchestrator에 반환한다.

---

## 2. 기존 시스템 분석

설계 문서를 작성하기 전에 관련 시스템을 조사한다.

- 프로젝트 구조 / 관련 모듈 / 공통 모듈 / 프로젝트 컨벤션
- 기존 DB 구조 / 기존 비즈니스 로직 및 API 처리
- 인증 및 권한

새로운 구조를 설계하기 전에 기존 구조를 재사용하거나 확장할 수 있는지 확인한다.
이 과정에서 소스코드를 읽고 분석할 수 있지만 수정하지 않는다.

---

## 3. 설계 범위 결정

요구사항을 기준으로 필요한 설계 영역만 판단한다.

가능한 설계 영역:

- Technology Stack (신규 시스템 또는 스택 변경 시 — `overview.md`에 편입)
- Database
- Business Logic (보안 설계 포함, 필요 시 API 설계 포함)
- Non-Functional Requirements (성능 / 확장성 / 가용성 / 관측성)

필요하지 않은 영역의 문서·섹션은 생성하지 않는다.

예 — DB 변경 + 로직 변경 + 외부 API 호출이 필요한 기능:
→ `database.md`, `logic.md`(「API 설계」·「보안 설계」 섹션 포함), `overview.md`.
신규 시스템이면 `overview.md`의 「기술 스택 및 주요 기술 결정」, 필요 시 `nfr.md`를 더한다.

예 — API가 전혀 필요 없는 순수 클라이언트 로컬 로직:
→ `logic.md`에 「API 설계」 섹션을 만들지 않는다.

# 문서 구조

```text
document/architect/
├── overview.md
├── logic.md
├── database.md
└── nfr.md
```

`overview.md`는 항상 작성하며, 「기술 스택 및 주요 기술 결정」 섹션에 스택 선정과 버전 고정을 포함한다.
나머지 문서는 해당 설계가 필요한 경우에만 생성한다.
**이 4개 외의 설계 문서는 생성하지 않는다.**

횡단 관심사(System Architecture / Authentication·Authorization / Error Handling / Data Flow 등)가
어느 문서에 담기는지는 `architect` 에이전트 정의의 「Design Scope」 영역→문서 매핑표를 따른다.

동일한 기능에 대한 기존 설계 문서가 존재하면 중복 생성하지 않고 기존 문서를 갱신한다.

---

# Database Document

DB 변경이 필요한 경우 `database.md`를 작성한다. 실제 DB 또는 Migration을 변경하지 않는다.

문서에는 필요한 경우 다음을 정의한다.

- 변경 목적 / 신규·변경·삭제 대상 / 엔티티 관계
- 테이블 / 컬럼 / 데이터 타입 / PK·FK / NULL 여부 / 기본값 / UNIQUE / 제약조건 / 인덱스
- 기존 데이터 영향 / 데이터 정합성 / 마이그레이션 고려사항
- DDL / 3건 이내의 임시 데이터 추가 DML

각 변경사항에는 가능하면 변경 이유를 함께 작성한다.

## 문서 규칙

- 모델명과 속성명은 대문자 스네이크 케이스(UPPER_SNAKE_CASE)로 작성한다.

---

# Logic Document

비즈니스 로직 또는 처리 흐름의 추가/변경이 필요한 경우 `logic.md`를 작성한다.
실제 로직을 구현하거나 수정하지 않는다.

`logic.md`는 다음 섹션으로 구성한다. (「API 설계」는 필요할 때만)

## 처리 흐름

- 목적 / 사전 조건 / 입력
- 정상 처리 흐름 / 조건 분기 / 상태 변화 / 데이터 변경
- 트랜잭션 범위 / 중복 요청 처리 / 동시성 고려
- 실패 처리 / 예외 처리 / 후속 처리

복잡한 흐름은 단계 또는 흐름도로 표현한다.

```text
요청 → 입력 검증 → 권한 확인 → 데이터 조회 → 정책 검증 → 데이터 변경 → 후속 처리 → 응답
```

## API 설계 (필요한 경우에만)

API 사용(신규 제공 API 또는 외부 API 호출)이 필요한 경우에만 이 섹션을 작성한다.
API가 필요 없으면 이 섹션을 만들지 않는다.

- API 목적 / Endpoint / HTTP Method / 호출 방향(제공 / 호출)
- Path Parameter / Query Parameter / Header / Request Body / Validation
- Response / HTTP Status / Error Response
- 인증 / 권한 / 처리 규칙 / 기존 API 영향
- 외부 API 호출 시: Timeout / Retry / 실패 처리 / 장애 영향

기존 API를 재사용하거나 확장할 수 있는 경우 해당 내용을 명시한다.

## 보안 설계 (항상 포함)

`.Codex/skills/_shared/conventions.md`의 「위협 열거 (STRIDE / OWASP)」를 참고하되
현재 기능과 관련된 위협을 중심으로 다음을 설계한다.

- 신뢰 경계와 공격 표면 (입력 지점, 외부 연동, 저장소)
- 인증 방식 / 세션·토큰 처리 / 권한 검사 지점 (Broken Access Control 대응)
- 입력 검증 및 출력 처리 (Injection / XSS 등 대응)
- 민감정보 식별과 보호 (저장 시 암호화, 전송 시 보호, 로그 마스킹)
- 비밀정보(키/토큰/자격증명) 취급 방식 (설계 수준, 실제 값은 다루지 않음)
- 의존성·구성 관련 위험과 대응 방향
- 감사/로그로 남겨야 하는 보안 이벤트
- 각 위협에 대한 대응책과 잔여 위험(residual risk)

기획에서 정해야 할 보안 정책(예: 데이터 보관 기간, 계정 정책)이 비어 있으면
임의로 정하지 않고 미결정 사항으로 반환한다.

# NFR Document

비기능 요구사항을 기술적으로 구체화해야 하는 경우 `nfr.md`를 작성한다.
기획서의 비기능 요구사항 장을 입력으로 받아 기술 목표와 설계로 구체화한다.
기획에 없는 목표치(SLA/SLO 등)는 임의로 신설하지 않고 미결정 사항으로 반환한다.

- 성능 목표 (응답시간 목표, 처리량, 기준 부하)와 이를 달성하기 위한 설계
  (캐시, 인덱스, 페이지네이션, 비동기 처리 등)
- 용량 / 규모 가정 (데이터 증가율, 동시 사용자, 피크 트래픽)
- 확장성 (스케일 아웃 지점, 상태 분리, 파티셔닝/샤딩 여부)
- 가용성 목표 (SLA/SLO, 허용 다운타임)와 장애 대응 (재시도, 폴백, 격리, Timeout)
- 관측성 (로깅 정책, 수집 메트릭, 분산 트레이싱, 알림 기준)
- 검증 관점 (Tester가 확인할 수 있는 측정 가능한 기준)

# Overview Document

`overview.md`는 개별 설계 문서를 종합하는 최상위 설계 문서다.
세부 DB/로직 내용을 그대로 반복하지 않고, 전체 구조와 설계 간 관계를 이해할 수 있게 요약한다.

최소한 다음을 포함한다.

## 설계 개요

기능 목적 / 설계 대상 / 변경 범위.

## 기획 검증 결과

`plan.md` 검증 결과 (설계 가능 여부, 발견된 미결정/반려 사유가 있으면 명시).

## 요구사항 요약

설계의 근거가 되는 핵심 요구사항. 근거가 된 기획 문서(`plan.md`)와 버전을 명시한다.

## 기존 시스템

관련 기존 구조와 재사용 또는 변경되는 영역.

## 전체 구조 및 처리 흐름

기능의 전체 기술 구조와 처리 흐름. 실제 구조에 해당하는 요소만 표시한다.

```text
Frontend → API → Business Logic → Database → External System
```

## 인증 / 권한 및 오류 처리 요약

인증·권한 모델과 주요 오류 처리 방침을 개괄한다.
상세 계약과 예외 흐름은 `logic.md`를 참조하고 여기서는 반복하지 않는다.

- 인증 방식과 세션/토큰 개요
- 권한 계층과 접근 제어 원칙
- 주요 오류 응답 방침 (공통 오류, 실패 시 사용자 데이터 보존 등)

## 보안 요약

`logic.md` 「보안 설계」의 핵심 위협과 대응만 요약하고 상세는 해당 섹션을 참조한다.

## 설계 문서

작성된 세부 설계 문서를 나열하고 각각의 목적을 간략하게 설명한다.
(예: `logic.md` — 주요 처리 흐름 + API 설계 + 보안 설계, `database.md` — 데이터 구조 변경,
`nfr.md` — 비기능 요구사항 구체화)

## 영향 범위

기존 시스템에서 영향을 받는 영역.

## 기술 스택 및 주요 기술 결정

기술 스택을 가정이 아닌 명시적 결정으로 기록한다.
기존 코드베이스가 있으면 그 스택을 따르고, 그 사실을 명시한다.

- 언어 / 런타임 (고정 버전 명시)
- 프레임워크 및 주요 라이브러리 (major 버전 명시)
- 데이터 저장소 (DB 엔진, 캐시, 검색 엔진 등)
- 인프라성 컴포넌트 (메시징, 오브젝트 스토리지 등)
- 각 선정의 근거와 검토한 대안
- 그 외 중요한 기술적 결정과 그 이유

## 비기능 요약

`nfr.md` 가 있는 경우 핵심 결정만 요약하고 상세는 해당 문서를 참조한다.
없으면 해당 요구가 없음을 명시한다.

## 미결정 사항

기획, 정책 또는 추가 확인이 필요한 사항.

---

# 문서 간 일관성 검증

모든 문서를 작성한 후 서로의 내용을 검증한다.
특히 API → Logic → Database 연결 관계와 보안 설계 정합성에서 다음을 확인한다.

- (API 설계가 있으면) API의 Request가 Logic에서 처리 가능한가?
- Logic에서 사용하는 데이터가 Database 설계에 존재하는가?
- Database 변경과 상태 변경 흐름이 일치하는가?
- 인증 및 권한 조건이 각 문서에서 일관되는가?
- 보안 설계의 신뢰 경계·검증 지점이 처리 흐름과 모순되지 않는가?
- 동일한 용어와 필드명이 문서마다 다르게 사용되지 않았는가?
- `overview.md` 요약이 각 세부 문서와 일치하는가?

불일치가 발견되면 관련 설계 문서를 수정한다.

---

# 금지 사항

이 Skill을 사용하는 동안 다음을 수행하지 않는다.

- 실제 소스코드 작성 또는 수정
- DB Schema 변경 / Migration 생성 또는 실행
- API 구현 / 비즈니스 로직 구현 / Page 또는 Component 구현 / 테스트 코드 구현
- 배포 설정 파일 / IaC 코드 / CI·CD 파이프라인 정의 파일의 생성 또는 수정
- overview / logic / database / nfr 외의 설계 문서 생성
- 서비스 정책 임의 결정
- 기획에 없는 서비스 수준 목표(SLA/SLO 등) 임의 신설
- 요구사항 임의 변경

코드는 기존 시스템 분석을 위해 읽을 수 있다.
설명에 필요한 경우 pseudo code, JSON 예시, SQL 형태의 구조 예시 등을 문서 안에서 사용할 수 있지만
실제 프로젝트 구현 파일을 생성하거나 수정하지 않는다.

완료 판정은 `architect` 에이전트의 「Completion Criteria」를 따른다.
